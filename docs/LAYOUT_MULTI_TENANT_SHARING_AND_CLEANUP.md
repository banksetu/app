# BANK SETU — Multi-template, shared design discovery and tenant-safe cleanup
Status: **REQUIREMENTS SPECIFICATION ONLY — NOT IMPLEMENTED OR RELEASED**.
Captured from the client discussion, 2026-11-03. This is part of draft PR #98. No code or production settings were changed by recording it.

## Core invariants (must never regress)
1. Each Client/tenant owns its **own** template slots (Layout 1, Layout 2, Layout 3, ...), copies, backups, restore history, activation choices, local source PDFs and deletion/tombstones. Master Admin access still follows existing permissions. **Deleting or overwriting tenant A's slot MUST NOT delete tenant B's slot, local cache, approval or active layout**, including if both originated from the same published generic bank design. No cross-tenant cascading delete.
2. A public/reviewed **bank design library entry** is an independent immutable or versioned **sanitized design-only** source. It never embeds account numbers, customer names, addresses, photos, signatures, scans containing real customer values, customer defaults, credentials or private tenant settings. Import into a client creates its own tenant-owned copy; client delete affects that copy ONLY. A shared bank design is never deleted by a tenant's local delete action.
3. Same tenant, multiple authorized logins/devices: all eligible users of that same tenant must discover the tenant's available templates, pending updates and active choices after online sync. Working design is cached locally for offline use; the local AI/OCR/PDF renderer and existing PR2 Bridge are NOT hosted in Firebase.
4. Different clients using the **same bank** may discover other clients' **explicitly published and approved generic designs**, subject to existing Master review, permission and bank match. Preview before importing. Preview must use EMPTY/fictitious fields or requesting client's own local customer data, NEVER another client's customer data or original PDF.
5. New shared template notification: show **"A new passbook design is available for your bank. Preview / Import / Skip."** on the authorized same-bank client. **Skip is not rejection or deletion**: hide that version's prompt for that user/tenant (version-scoped) but keep it in the permanent **Other designs available / Browse designs** menu so it can be previewed/imported later. Do not repeatedly spam skipped prompts. Do not silently overwrite an existing bank slot.
6. Passbook and Passbook Print customer search runs ONCE and binds the same **current customer's data** to each existing local template. Show dynamic **Layout 1, Layout 2, Layout 3… tabs** above the preview; switching tabs changes only the layout, not the selected customer or tenant. Pressing Print must use the **currently visible tab**. No separate selection page needed.
7. **Direct PR2/Olivetti output ONLY belongs to the Passbook Print menu**, using the already installed PR2 Bridge, and contains only bank-approved dot-matrix **text labels/values** (Union Bank: values only). NO logo, customer photo, graphics, source PDF page or alternative printing engine is sent to PR2. Quick Passbook continues independently with its own permitted graphics and photo.
8. Upload PDF is a **local source document**, not a permanent cloud blob. The user must be able to delete ONE upload or **all old uploaded PDFs** for their own tenant from local app storage; never remove generated templates or other tenants' files. At successful conversion offer **Delete source PDF now / Keep for corrections**; optional auto-clean after confirmed successful template generation and locally persisted geometry, with a clear undo-unsafe warning. Do not auto-delete before the user has verified a usable editable layout, and never delete source from an uncommitted or failed import. If a scan contains private text, it must not enter shared approved design metadata or telemetry.
9. Template deletion requires BOTH explicit **"Really delete this template?"** confirmation identifying slot/bank AND secure account reauthentication (user requested client password). Never store/compare raw passwords in app/Firestore/template. For Google/OAuth-only sessions use the existing provider's secure reauthentication, not a nonexistent password. A Master Admin uses their OWN authorized reauthentication, not the client's password. If offline validation is unavailable, queue a request or require online reauthentication; **do not silently finalize a remote delete**.
10. Delete/restore/replace actions are scoped by a compound identity (**tenant ID + bank key + mode + slot ID + revision**) on the server and existing local data access boundary. Implement revision compare-and-swap and race handling, a recoverable pre-delete snapshot/soft-delete window and existing offline deletion tombstone semantics. Avoid resurrecting stale deleted records on an older device. A deleted ACTIVE slot should require an explicit fallback choice, never silently fall back to a different tenant's or unreviewed design.
11. Registration asks **"Which template slot should this design use?"**, previewing which occupied slot would be replaced and offering **Create new slot**. Backup asks **"Which template(s) do you want to back up?"** (1/2/3/all), Restore asks which destination slot and confirms replacement, with backup-before-replace.
12. To support new devices, cloud must store enough **small sanitized compressed generic layout payloads** (or encrypted/restricted content-addressed backups) to reconstruct the complete list, not IDs alone. Minimize Firebase storage and reads with per-template ID, hash, version, status and delta/on-demand downloads. Original PDFs/images and OCR/AI models stay local. Local-first cache uses the **existing** BANK SETU local DB/IndexedDB and sync architecture; never build competing engines.
13. The original approved Assam Gramin, PNB, Union, Central Bank and all legacy bank print flows are preserved unless the specific tenant explicitly previews and activates an approved layout. PNB and Union print rules stay unchanged. Old backups remain restorable. No unreviewed Firebase production mutation; Spark plan compatible.
14. Release policy: perform all possible code, worker, mock bridge, browser, PDF and Windows/Android packaging tests BEFORE One Click Release; actual physical Windows/Android/Epson printer tests take place AFTER the approved version release, then corrective releases as needed. Passing software tests is not physical hardware certification.

## Suggested small-data model (proposal, not code)
- `sharedBankDesign/{bankKey}/{versionId}`: immutable sanitized source design, publishedBy opaque owner, approval status, checksum, size, createdAt, approvedAt. No private bank or customer information, no source PDF.
- `tenant/{tenantId}/layoutSlots/{bankKey}/{mode}/{slotId}`: tenant-owned selected source design/copy, slot name, local revision, content hash, cloud compact backup reference, selected status, tombstone state.
- `tenant/{tenantId}/templateBackups/{backupId}`: tenant-owned compressed sanitized design snapshot, matching hash/version/slot; keep strict size quotas and bounded retention.
- `tenant/{tenantId}/designDiscovery/{sourceVersionId}`: offered/seen/skipped/imported state; a skipped version remains searchable and importable later.
- On local devices: existing indexed/local layout storage has editable current slot contents and the list of source-PDF references with client/tenant ownership and automatic cleanup options.
- Shared library entries MUST be distinct from tenant copies to ensure one tenant's delete cannot affect others. Never expose source tenant identity/records in a public preview unless separately authorized.

## User-visible flow — unchanged customer search
1. Search Account Number once and load the authorized client customer ONCE.
2. Read the tenant's cached template list and show as many tabs as present: **Layout 1 | Layout 2 | Layout 3 | ...** (virtualize/scroll if many).
3. Each tab displays that SAME customer's mapped data in the tab's distinct physical dimensions and output rules; print button prints the visible active tab ONLY.
4. Quick output uses graphics/photo where allowed. Passbook Print **only** uses the approved dot-matrix layer through the EXISTING PR2/Olivetti engine.
5. Other designs are offered separately under **More designs available** (Preview, Import into Slot, Skip), without wiping any active tab.

## Software-level acceptance tests to implement
- Two tenants import the same shared generic template; deletion/replacement of tenant A's slot leaves B's copy, B's active setting and shared source identical.
- A client can neither read nor delete another client's uploaded scans, backups, skipped design state or layout slots; wrong bank/mode and unauthorized role are denied.
- One tenant logs in with another authorized account or new device, discovers all template slots after first sync, downloads only missing/changed compressed versions, works offline thereafter, and remains isolated from other tenants.
- Publish/offer/preview/skip/reopen/import shared design without changing an existing active layout until explicit slot selection and activation.
- Same-customer binding across 1/2/3 tabs, no refetch on tab switch; quick and PR2 outputs differ correctly; in-flight print is bound to tab/template revision chosen on print, not changed mid-spool.
- Delete needs explicit slot confirmation + server-authorized recent reauth; wrong password, expired token, offline or missing permission MUST NOT delete remote template; double-click/double-submit is idempotent; conflicts do not erase other slots.
- Delete active slot proposes explicit fallback/restore; soft delete, offline tombstones and backup/restore prevent resurrection or destructive cross-tenant sync.
- Register/overwrite always asks target slot; backup asks source slot; restore asks target slot and preserves the previous state.
- Import successful / unsuccessful / canceled: only user-approved and tenant-owned source PDF cleanup is permitted; delete-one/delete-all never removes finalized layout, backup or other client files; any pending OCR/reference dependence is disclosed.
- All bank/PR2 regression, Worker/tenant security, Android debug APK, Windows installer, Web and performance/size-budget checks pass; physical checks remain separately sign-off gated.

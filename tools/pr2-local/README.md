Never delete production files or pending printer jobs blindly.

TX and RX logs include timestamps, raw hex, partial replies/timeouts, strict parser results, paper state and post-action checks. Unknown bytes are preserved and stop motion. ## Diagnostic v2 / controller pilot — 2026-10-21

Epson-authored PLQ-20/PLQ-20M Programming Guide NPD0841-00 Rev A, sheets 73, 76–79 and 83 (https://www.installing.ru/files/plq20pg_e.pdf): ESC Z returns ESC / 7 in PR2; ESC j returns ESC r x. ESC n starts the procedure and has no documented identity response. Therefore the actual repeated 1B 2F 37 is not status and proves neither readiness nor paper presence. Current data cannot distinguish stale/duplicated input, transaction buffering, firmware state or interface behavior. No protocol mode change/reset is attempted.

The isolated helper uses FileStream buffer size 1 instead of 4096 to avoid managed read-ahead. A new bounded capture operation logs entire response windows (256-byte maximum, 1500-ms overall window, 1000-ms first-byte and 150-ms inter-read quiet period), read segment offsets, lengths, timing, cancellation-race bytes and capture limits. Native write acknowledgements and TX logs are distinct from printer acknowledgement. It captures before any command, after control-start, and after each identity/status/paper request; unknown/mixed frames are retained and never skipped into a false ready state. These windows show temporal association, not guaranteed firmware causality. The development branch carries the same bounded capture in the desktop Bridge; the installed EXE, strict parser, IPC and approved layout remain unchanged.

## Encrypted GitHub mailbox evaluation (PR #58 continuation)

Transport feasibility is no longer the same as private key custody. Available connector actions actually include create_file/update_file/fetch_file (explicit branch/ref), create_tree/create_commit/update_ref, PR metadata, workflow/artifact reads and failed-job reruns. There is no exposed arbitrary POST/workflow_dispatch, repository-secret read, Windows token handoff, managed signing/decryption operation, or durable protected private-key store. The connector authenticates GitHub calls internally; its token is not exported to Windows. No email/account reconnection is needed.

A fixed repository/branch mailbox adapter is implemented in mailbox.cjs. It uses authenticated Contents API calls with redirects forbidden, finite response/timeout limits and opaque UUID paths. Create-only jobs/results cannot silently replace earlier results. A protected local credential provider must supply the Windows token; the current code does not provision or persist one. The fine-grained Contents write permission is repository-scoped, NOT path/branch-scoped: do not represent it as a mailbox-only token. Using it on the main computer requires secure local storage and explicit acceptance of that scope, or a narrower dedicated broker. Neither permission nor token has been requested or provisioned. Documentation: https://docs.github.com/en/rest/repos/contents and https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens.

mailbox-crypto.cjs seals job/result contents with ephemeral X25519, HKDF-SHA256 and AES-256-GCM and authenticates sender with pinned Ed25519 keys. The authenticated header binds pairing UUID, job UUID, message type and recipient key fingerprint. Job inner signatures remain subject to the existing five-minute expiry, paired device/bundle checks, action allowlist and durable replay ledger. Public Git history contains ciphertext plus opaque routing IDs/types, size and timing metadata; it is not a private GitHub ACL and deletion cannot promise erasure. Real customer data must never enter the test agent at all. No production key is generated, committed or included in CI. Transport/crypto tests use throwaway synthetic keys only and do not prove independent cryptographic audit or real hardware success.

mailbox-session.cjs tests the encrypted job -> durable diagnostic engine -> encrypted result -> upload path, including upload failure/restart without printer replay. Only encrypted packets can enter its HTTP publish path; no raw device logs or token is intentionally sent to public GitHub content/issues/artifacts. The receiver verifies signatures and decrypts locally through its approved key custody boundary. Execution errors after durable acceptance are encrypted too; duplicates/expired jobs cannot overwrite results. A crash between execution and result sealing remains uncertain and does not rerun USB. Automated component installation remains disabled.

## Physical partial-print correction (2026-10-23)

The real PLQ-20 run proved visible 24-pin raster output and one front return, but only part of the synthetic passbook reached paper. A USB write acknowledgement is not mechanical completion. The agent now sends one complete 24-dot band, queues `ESC } W`, requests status with `ESC j`, and requires the strict `ESC r P` READY frame before sending the next band. It never retries a band. After the final READY it confirms the document is still inserted, waits once, and sends one `ESC O`.

The synthetic test bitmap uses the same `WordPassbookInfo` glyph paths and field anchors as the approved Assam layout. Its isolated proof flag uses Courier New 10 pt, 70% horizontal width and the requested 1 px tracking; the normal application default remains 10.2 pt / 1.5 px and is not changed. Complete text rows are kept inside one 24-pin band so a glyph is not divided between independently positioned bands. Transport removes only empty horizontal bytes; it does not fit, reflow or move field anchors. Physical fidelity, completeness and front release still require human confirmation.
